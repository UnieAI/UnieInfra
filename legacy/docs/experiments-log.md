# UnieInfra Experiments Log

Every experiment is recorded here — **successes AND failures**. A failed test is
data: it stops us (and the community) from repeating dead ends, and it usually
points at a root cause worth fixing. Rejected approaches keep their reason.

Hardware unless noted: **1× NVIDIA RTX PRO 6000 (sm_120)**, in the
`nctu6/unieinfra-autobuild-dev:cuda-12.9.1-blackwell_only` container
(nvcc 12.9, torch 2.11.0+cu129). Model unless noted: **Qwen3-8B (dense, bf16)**.

The gate is `os.path.basename(sys.argv[0])`, and a test asserts the `vllm` path leaves `speculative_config`, `kv_cache_dtype`, `kv_offloading_size` and `enable_prefix_caching` all at their sentinels — so the two arms of any A/B can be one binary. `unieinfra serve --help` now reads `usage: unieinfra serve [model_tag] [options]` and `unieinfra --help` reads 'UnieInfra CLI — OpenAI-compatible LLM serving'; `vllm serve --help` still reads `usage: vllm serve`. The OpenAI HTTP API is untouched — this is the launcher and the configuration surface, not the wire protocol. **(1) MTP AUTO-ENABLES FROM THE TENSOR INDEX, NOT FROM THE CONFIG — AND THAT DISTINCTION IS LOAD-BEARING.** The probe requires *two* signals to agree: a positive MTP layer count in the HF config (any of `num_nextn_predict_layers` / `mtp_num_hidden_layers` / `num_mtp_modules`, at top level or under `text_config`, which is the complete set `SpeculativeConfig.hf_config_override` reads) **and** MTP tensors actually present in `model.safetensors.index.json`. A config that *declares* an MTP head whose weights were never published is treated as unsupported, because the config is a promise and the tensor index is the fact; a test pins that case. Measured on disk: **Qwen3.6-35B-A3B 19 `mtp.*` tensors → MTP ON, Qwen3.5-27B 15 → ON, gemma-4-31B-it 0 → off, gemma-4-26B-A4B-it 0 → off, Qwen3-8B 0 → off.** A remote Hub id that is not a local directory also declines, because MTP weights cannot be verified without downloading — stated in the reason string rather than guessed. Dry-run confirms the 35B resolves architecture **`Qwen3_5MoeMTP`** and loads the draft model; the Gemma 4 pair start clean with no speculation and no error. **This is the self-configuring principle (P4) doing real work: the same command line produces speculative decoding on one checkpoint and not on another, and the user never learns the word MTP.** **(2) THE DEPTH LADDER IS UPSTREAM'S MECHANISM, NOT OURS — AND SAYING SO CHANGES THE ATTRIBUTION CLAIM.** `docs/design/adaptive-speculative-decoding.md` was written against the retiring tokenspeed engine and argues for a small discrete depth set selected per step. That mechanism **already exists in this vLLM pin**: `SpeculativeConfig.num_speculative_tokens_per_batch_size`, a list of inclusive `(batch_lo, batch_hi, k)` rungs expanded into a dense lookup at `v1/spec_decode/dynamic/utils.py` and read by the scheduler at `v1/core/sched/scheduler.py:246`. So no scheduler fork was needed and none was written. Our default ladder is **`[(1,32,3), (33,128,2), (129,4096,1)]`** with `num_speculative_tokens=3` — deep at low batch, shallow at high batch, because speculation trades FLOPs for decode steps and FLOPs are the scarce resource at saturation (E39: +92%..+117% out tok/s at C=1 decaying monotonically to +39%..+65% at C=64). A test asserts the ladder is non-increasing and that `num_speculative_tokens` equals its maximum, since vLLM clamps every rung with `min(num_speculative_tokens, rung_k)` and a smaller static value would silently cap the ladder. **TWO COSTS, BOTH REAL, NEITHER HIDDEN.** (a) The ladder does **not** reclaim KV capacity — the pool is sized from the static maximum, so E39's 'k=3 costs 56% of the KV pool' is paid at every batch size. (b) The ladder **downgrades CUDA graphs**: the dry-run emits `Dynamic speculative decoding changes the target verification length at runtime. Overriding cudagraph_mode from FULL_AND_PIECEWISE to PIECEWISE`. Given E44 measured 637 kernel launches and 98.23% GPU-busy in a C=128 decode step, losing full graphs is not free, and whether the ladder beats a static k=3 is now an open measurement, not an assumption. `UNIEINFRA_SPEC_SCHEDULE=static` pins one depth and keeps full graphs. **Upstream's implementation has no hysteresis** (§6 of the design doc); it is a pure per-step dense-array lookup. That is cheaper here than in tokenspeed — vLLM does not re-point CUDA-graph stacks per depth — so the dead-band was deliberately NOT implemented rather than faked, and the gap is recorded instead. **(3) fp8 KV IS SHIPPED OPT-IN, AND THE REASON IS A MEASURED PROPERTY OF THIS HARDWARE.** The brief asked for it as a default *and* asked whether attention truly reads fp8 or upconverts. It upconverts — or worse, silently changes backend. `flash_attn_supports_kv_cache_dtype('fp8_e4m3')` returns **False on sm_120**: FlashAttention accepts fp8 KV only on the SM90 (FA3) and SM100 (FA4) *families* (`v1/attention/backends/fa_utils.py`, via `is_device_capability_family`), and refuses with 'FP8 KV cache requires FA3 on SM90 or FA4 on SM100'. vLLM does **not** surface that: with no explicit `--attention-backend` it drops FlashAttention from the candidate list, logs the reason at `logger.debug_once` (invisible at default level) and picks the next backend (`platforms/cuda.py:427-455`). Which backend that is turns out to be model-dependent — Triton attention reads fp8 natively on SM89+, whereas **FlashInfer's TRTLLM prefill path dequantizes fp8 pages into a freshly allocated bf16 buffer whenever the query is bf16** (`backends/flashinfer.py:1987-2018`, kernel `_trtllm_prefill_attn_kvfp8_dequant`), and bf16 query is exactly the sm_120 configuration because FlashInfer's query quantization is gated on the SM100 family. **That path pays the quantization error and the dequant traffic and delivers none of the bandwidth saving — strictly worse than not quantizing.** **THIS RETIRES E44's HEADLINE PROJECTION, AND THAT MATTERS FOR THE ROADMAP.** E44 finding (9) named fp8 KV 'the biggest single change' available, projecting attention 13.36 -> 6.68 ms and **+30.6% aggregate throughput at C=128**, on the assumption that halving KV bytes halves KV read time. **That assumption does not hold on sm_120**, and E44 flagged its own number as a projection rather than a measurement. The arithmetic only works if the attention kernel *reads* fp8; here the kernel that would deliver it (FlashAttention, which E44 profiled -- `flash_fwd_splitkv`, 46.9% of the step at DRAM 91.9% of peak) is precisely the one that refuses fp8 KV outside SM90/SM100, so enabling fp8 moves the workload OFF the kernel whose bandwidth the projection was computed from. The realistic sm_120 outcome is **capacity without bandwidth**: KV pages get half as large, and on the FlashInfer fallback the prefill path spends *extra* traffic dequantizing them back to bf16. **So +30.6% is not available on this hardware and should not be carried in any plan; the fp8 KV lever is a capacity lever here, not a bandwidth lever.** It remains a real bandwidth lever on SM90/SM100 parts (H200, B300 in the compat matrix), which is exactly where FA3/FA4 accept it -- so this is a per-part conclusion, not a retraction of fp8 KV in general. Add that the accuracy question is still open (a separate GSM8K/HumanEval run at bf16 vs fp8_e4m3 vs fp8_e5m2 was in flight as E48, and was stopped once fp8 shipped opt-in, since its answer no longer gates the product) and the honest call is opt-in: `UNIEINFRA_DEFAULT_KV_FP8=on` or `--kv-cache-dtype fp8`, one switch, no code change. **A converged product with three defaults and an honest note beats four defaults and a footgun.** Two further facts worth recording: fp8 KV *does* apply to Gemma 4's sliding-window layers (`SlidingWindowSpec` is built with the quantized dtype) unless `--kv-cache-dtype-skip-layers sliding_window`; and it **never** applies to GDN/mamba state, which is governed by `mamba_cache_dtype`/`mamba_ssm_cache_dtype` whose `MambaDType` Literal has no fp8 member at all — so on Qwen3.6-35B-A3B fp8 KV could only ever quantize the 10 full-attention layers of 40. **(4) KV OFFLOAD IS ON, SIZED FROM MEASURED RAM, AND PROVEN NOT TO BE E17.** E17 OOM-killed a server at startup on a 139 GB host allocation because the retiring engine defaulted `kvstore_ratio=2.0` — a host pool twice the *device* pool. vLLM's own equivalent (`kv_offloading_size`, GiB, → `OffloadingConnector` with `cpu_bytes_to_use = size << 30`) is off by default and takes mandatory absolute bytes. We default it ON but derive the number: **`min(10% of available host RAM, 32 GiB cap, available − 64 GiB reserve)`**, refusing entirely below an 8 GiB floor or if `/proc/meminfo` `MemAvailable` cannot be read ('refusing to guess'). On this 999 GB host that yields **32 GiB with 917 GiB left untouched**, and the dry-run confirms `kv_connector: OffloadingConnector` on all four models. The sizing matters because the buffer is **eagerly `torch.zeros`'d and page-locked** at `register_kv_caches` time (`v1/kv_offload/cpu/gpu_worker.py:477-508`) — `torch.zeros` not `torch.empty`, so there is no lazy first-touch and the RSS is real before the first request. Tests pin that a 48 GiB host gets nothing and that a 512 GiB cap still cannot exceed the RAM fraction. **AND THEN ACTUALLY BOOTING IT FOUND A REAL BUG THAT EVERY CONFIG-LEVEL DRY-RUN HAD MISSED — THE FIRST LIVE LAUNCH OF THE FLAGSHIP MODEL DIED AT STARTUP.** `unieinfra serve Qwen3.6-35B-A3B` raised `AssertionError: tokens_per_block=4096 not divisible by tokens_per_hash=274432. Hybrid models (e.g. Mamba+Attention) need --enable-prefix-caching to align block sizes` from `kv_connector/v1/offloading/config.py:52`. The pair is **unsatisfiable by construction**: the offload connector demands prefix caching on hybrid models, and vLLM force-disables prefix caching on exactly those models — so 'KV offload ON by default' plus 'hybrid model' is a guaranteed boot failure, violating this layer's own rule 2 (auto-degrade, never fail). `create_engine_config()` does **not** catch it because the assertion fires in the connector's constructor during `register_kv_caches`, long after config resolution; **only starting the engine finds it.** Fixed with a `probe_is_hybrid_model()` check (reads `layer_types` from the HF config, so Gemma 4's `sliding_attention`+`full_attention` is correctly NOT hybrid while Qwen3.6-35B-A3B's `linear_attention` is), which declines the offload default on hybrids with a logged reason; three tests pin it, including that MTP stays on independently. **The lesson generalises: a defaults layer cannot be validated by config dry-runs alone, because the interactions that kill you live in worker construction.** Otherwise nothing forbids offload + MTP + fp8 together; the offload scheduler explicitly accommodates EAGLE/MTP by excluding the volatile trailing chunk. **(5) PREFIX CACHING IS LEFT ON `auto`, WHICH IS NOT THE SAME AS ON — AND ON THE FLAGSHIP MODEL IT IS OFF.** Forcing `True` would convert 'this model cannot' into a startup error, so the tri-state is deliberately left `None` for vLLM to resolve as `is_prefix_caching_supported and not is_hybrid`. Dry-run result: **gemma-4-31B-it and gemma-4-26B-A4B-it → `prefix_caching_enabled: true`; Qwen3.6-35B-A3B → `is_hybrid: true`, `prefix_caching_enabled: FALSE`.** So the GDN hybrid runs **two** of the four defaults (MTP + offload), not four, and the startup banner says so rather than quietly reporting a four-default result. E39b's measured value of prefix caching (cold +23.1% throughput / −64.2% TTFT, warm +26.6% / −82.9%) is therefore unreachable on that model and fully available on the Gemma 4 pair. **(6) THE PRODUCT IS PROVEN TO SERVE, AND MTP IS PROVEN TO ENGAGE RATHER THAN NO-OP.** After the hybrid fix, `unieinfra serve /workspace/models/Qwen/Qwen3.6-35B-A3B --max-model-len 4096 --gpu-memory-utilization 0.85` boots clean on GPU 3, logs `Detected MTP model. Sharing target model embedding weights with the draft model` and `... lm_head weights ...`, resolves `enable_prefix_caching=False` (hybrid) and no KV connector, and returns coherent greedy text ('Paris, a city renowned for its rich history, culture, and iconic landmarks...'). **Speculative decoding is confirmed live from Prometheus and from the bench client, not assumed:** a warm 8-prompt C=1 run reports **acceptance rate 74.39%, acceptance length 3.23 of 4, 1,334 drafts / 4,002 draft tokens / 2,977 accepted**, with per-position acceptance decaying 84.48% / 75.11% / 63.57% — and `draft_tokens = 3 x drafts` independently confirms the ladder's **k=3 rung is the one active at low batch**, which is the adaptive policy doing what it was configured to do. Median TPOT on that run was 5.95 ms. **THE FULL SWEEP IS STILL INCOMPLETE, THE BOX WAS NEVER QUIET, AND ONE SET OF MY OWN CELLS WAS DISCARDED FOR A SELF-INFLICTED REASON WORTH RECORDING.** I launched the arm-A bench client **twice** -- the first invocation's stdout was buffered and no result files had appeared, so I concluded it had failed when it was simply still running. From 18:52:45 the two clients drove the **same server concurrently while writing the same filenames**, so `A_r1_c32.json` (18:53:38) and `A_r1_c128.json` (18:58:05) measure an unknown mixture of two load generators and are **void**; they are quarantined under `benchmark/results/e49/_discarded/` with a README rather than deleted. **AND THE DAMAGE WAS WORSE THAN THE FIRST DIAGNOSIS: ALL THREE CELLS WERE LOST, NOT TWO.** `A_r1_c1.json` was initially judged clean because it was written at 18:52:22, before the second client started -- but its mtime on disk is **18:58:56**, i.e. the second client's own C=1 cell **overwrote it** while the first client was still running C=128. The two clients shared a filename template, so each cell was written twice from different load conditions and the surviving bytes are the contaminated ones. A figure of 214.1 out tok/s / TTFT 98.2 ms / TPOT 4.22 ms / acceptance 77.3% was read out of the pre-overwrite version of that file and quoted in an interim report; **it is withdrawn**, because the artifact backing it no longer exists and it cannot be reproduced from what is on disk. A number whose evidence has been overwritten is not a measurement. **The generalisable lesson: absence of output from a background benchmark is not evidence that it died -- check for a live PID before relaunching, because a duplicate load generator is invisible in the result JSON and silently corrupts exactly the high-concurrency cells that matter most.** Separately, the box was reported cleared but was not: a co-tenant `VLLM::EngineCore` took 86 GB of GPU 1 at 18:54 and a **bench client on port 8448 (not ours) was running at 18:59**, so any arm-A-vs-arm-B pair measured in that window would have a neighbour whose load differs between arms -- the precise confound that voids an A/B. **No A-vs-B or A-vs-D table is reported, because none was legitimately obtained.** The brief said the other agents had been stopped; `nvidia-smi` said otherwise for the entire session. At start: four live `VLLM::EngineCore` processes, three of them seconds-to-minutes old (GPU 0 = another user's 33-day embedding server, never touched; GPU 1, 2, 3 all inside the `unieinfra-vllm-build` container we share). GPU 1 is deliberately claimed by another agent's **`e48_gpu_hold.py 1 4`** — the E48 fp8-accuracy run this experiment depends on. GPU 3 went briefly to 0 MiB and our hold **lost the race by 12 seconds** to a co-tenant EngineCore that took 80,000 MiB. Our own 4 GiB hold (PID 236964) remains on GPU 3 so the card is ours when that tenant exits. **No process belonging to another agent was killed, and no pattern-matching kill was issued** — the E47 lesson. With models at 49–67 GB on 96 GB cards, a 4-arm sweep needs a nearly-empty card and none existed. **Nothing was fabricated to fill the tables; they are simply absent.** **(6b) THE CONTROL ARM DOES NOT BOOT ON THIS MODEL, AND THE REASON IS THE MOST INTERESTING RESULT SO FAR.** `vllm serve Qwen3.6-35B-A3B --max-model-len 4096 --gpu-memory-utilization 0.85` — upstream defaults, our binary — **fails at startup**: `ValueError: max_num_seqs (1024) exceeds available Mamba cache blocks (500). Each decode sequence requires one Mamba cache block, so CUDA graph capture cannot proceed`, raised from `config/compilation.py::resolve_cudagraph_mode_and_sizes`. The default `max_num_seqs=1024` is simply larger than the GDN state pool this model affords at this utilisation, and the engine **raises instead of clamping**. **`unieinfra serve` boots on the identical box and flags — but NOT because our defaults are wiser.** It boots because the adaptive speculative ladder has already forced `cudagraph_mode` from `FULL_AND_PIECEWISE` to `PIECEWISE`, and the failing check lives on the full-capture path, so we never reach it. **That is dodging a check by degrading CUDA graphs, and it must not be reported as a product win.** It is, however, a genuine and quotable fact about the *out-of-the-box experience* on a hybrid MoE: ours starts, upstream's does not. **Mitigation for the comparison:** arm B is given `--max-num-seqs 500`, the minimum intervention that lets the control start. It is **non-binding at every concurrency tested** (max 128, far below 500), so it cannot flatter either arm; it is passed through an explicit `ARM_B_EXTRA` so it appears in the command line rather than hiding in the harness. **(6c) A SECOND CONTAMINATION, WITH A SHARPER LESSON THAN THE FIRST.** A helper script from the abandoned first attempt was orphaned rather than killed — the PID namespaces of the host and the `unieinfra-vllm-build` container **differ**, so `kill` issued from the host targeted a *different* process than the same number inside the container, and a `docker exec` kill reported success against the wrong PID entirely (the same mismatch is visible in E48's holder, which prints `pid=266186` while `nvidia-smi` reports `236964`). The orphan's own server had died on the very `max_num_seqs` error above — **but its health check polled a fixed port, got a 200 from OUR arm-A server on that port, declared itself healthy, and benchmarked against it**, writing `B_r1_c*.json` files that carry arm A's speculative-decoding fingerprint (`acceptance_length 3.28` on an arm that has no drafter). It was caught by exactly that tell. **Two lessons: (i) always resolve PIDs in the namespace you intend to kill in, and verify the process is gone rather than trusting kill's exit status; (ii) a health check against a fixed port proves a server is listening, NOT that it is YOUR server** — every arm should verify identity (model name, config fingerprint) before trusting a port. The affected rep-1 cells were discarded and the sweep restarted from a verified-clean slate at 19:11:33. **(6d) THE THIRD ATTEMPT DIED IN THE MOST EXPENSIVE WAY AVAILABLE: A SILENT DEADLOCK.** The clean restart (19:11:33, verified single server / single client, arm identity confirmed as `unieinfra serve`) reached `arm A rep 1 C=1` at 19:13:04 and then **produced nothing for 52 minutes with the GPU at 0% utilisation**. The server log shows why and also shows why it was invisible: at 19:13:27, 23 seconds into the first cell, `[launcher.py:100] [shutdown] API server: shutdown triggered` with **no preceding error**, followed by `Waiting for connections to close` and a steady-state `Running: 1 reqs` / `generation throughput 0.0` forever. The engine deadlocked draining one in-flight request; the bench client blocked on a response that would never arrive; and **no process exited, so nothing in the harness noticed**. The trigger could not be attributed from any log -- no signal source is recorded -- and it is not the `max_num_seqs` failure of (6b), which raises loudly at startup. **This is the worst failure mode a benchmark harness can have: it looks identical to 'still running'.** Three hardenings were made rather than root-causing further: (i) each cell is now wrapped in `timeout --signal=INT --kill-after=60 ${CELL_TIMEOUT:-1500}`, so a hung cell costs 25 minutes at most instead of unbounded time; (ii) `/health` is re-checked **before every cell**, and the arm is aborted rather than allowed to hang if the server is not answering; (iii) the server is started with stdin redirected from `/dev/null` so a closing `docker exec` session cannot deliver it a signal. **NO A-vs-B TABLE WAS OBTAINED.** Three sweeps were attempted: the first was voided by my own duplicate client, the second by an orphaned helper benchmarking through a shared port, the third by this deadlock. Between attempts the box was repeatedly re-occupied by other agents -- GPU 3 was taken by an 84.7 GB process within minutes of each release -- so no fourth attempt was started. **Everything reported for this experiment is therefore about the PRODUCT, which is verified end-to-end, and nothing is reported about its SPEED, which is not measured.** The harness, the summarizer and its arm-identity guard are in the tree and ready; what is missing is an uninterrupted GPU. **(7) THE ARM DESIGN IS BUILT AND IS DELIBERATELY FOUR ARMS, NOT TWO — BECAUSE TWO CANNOT ATTRIBUTE.** `benchmark/scripts/run_e49_product_ab.sh` implements: **A** `unieinfra serve` (our engine, our defaults — the product); **B** `vllm serve` on the *same binary* with `UNIEINFRA_GEMM=0 UNIEINFRA_ATTENTION=0 UNIEINFRA_QUANT=0` (isolates the defaults, and only the defaults, since the only variable is which script name was typed); **C** arm B plus the equivalent features enabled by hand (separates 'our defaults are good' from 'we switched on what vLLM already had'); **D** the genuinely separate stock vLLM 0.25.1 install at `/home/ubuntu/vllm-bench-venv` out of the box (external reference — and the only arm whose engine version differs, so a D delta must never be attributed to defaults). **A CONFOUND FOUND WHILE BUILDING ARM C, which would have silently broken the attribution table:** stock vLLM 0.25.1 **has no `num_speculative_tokens_per_batch_size` field at all** (verified against its `SpeculativeConfig`), so arm C can only run a *static* k=3. The adaptive ladder is therefore not comparable between arm A and arm C — and it is not a UnieInfra invention either, it is a newer-upstream feature we chose to turn on and pick rungs for. Stock 0.25.1 *does* register `Qwen3_5MoeForConditionalGeneration`, **`Qwen3_5MoeMTP`** and `Gemma4ForConditionalGeneration`, so arm C genuinely can run MTP on the 35B and the arm is fair on that axis. ## Failures & root causes (the useful part)

- **Mixed prefill+decode batching is unreachable on sm_120 — E31.** Not a scheduler
  gap: the C++ scheduler already composes mixed plans correctly under
  `enable_mixed_prefill_decode`, and the runtime already classifies, samples and
  post-processes them (`ForwardMode.MIXED`). The wall is **attention metadata**.
  Every MHA-arch backend we can run (`mha`/`fa3`/`fa4`/`triton`/`flashinfer` — all
  one `MHAAttnBackend`) rejects MIXED because its extend path has no decode tail,
  and the one MHA backend that does support MIXED (`trtllm`) is TRT-LLM-gen FMHA,
  sm_100/103 only — the same wall as E11. The remaining mixed-capable backends are
  MLA-only. **Cost of the gap, measured:** at C=256, 7.8% of steps are prefill-only
  but they consume **38.6% of wall clock with zero decode progress**, in bursts of
  up to 33 consecutive steps (~11.5 s of total decode starvation). Fix is scoped:
  synthesise `extend_seq_lens`/`extend_prefix_lens` for the decode tail in
  `MHAAttnBackend.init_forward_metadata`. Until then `--enable-mixed-batch` is
  refused at startup rather than crashing mid-serve.
- **flashinfer version skew — E5, E11.** The container has `flashinfer-python 0.6.15`
  (caller) but `flashinfer-jit-cache 0.6.12` (precompiled kernels). Their signatures
  disagree (MoE `init` 7-vs-8 args; attention `trtllm_paged_attention_context`
  31-vs-32 args). `FLASHINFER_DISABLE_VERSION_CHECK=1` silences the check but not
  the ABI mismatch. **This one root cause blocks ALL flashinfer paths on sm_120.**
  Fix under investigation: align `flashinfer-jit-cache` to 0.6.15, or force JIT.
- **MoE bf16 unquant on sm_120 — E5, E6 → E14 → RESOLVED in E28.** `ops/moe/triton/`
  covers only quantized weights; unquant bf16 had only the flashinfer path. The
  flashinfer version alignment (E14) made that path usable, and **E28 ran the full
  Qwen3.6-35B-A3B model end-to-end with correct output**. Note E28 **corrects** E14's
  predicted cause: the `cutlass_unquant.py:96` `token_final_scales` dtype is real but
  **only reachable by direct callers**, not by the engine (the kernel advertises
  `routing_mode=precomputed_topk`, so the engine supplies float32 scales itself). The
  actual blocker was the triton MHA prefill tile overflowing sm_120 shared memory at
  head_dim=256 — see the next bullet. Porting a bf16 `fused_experts` into
  `ops/moe/triton/` remains the portable long-term option (scoped in E28: the routing,
  swiglu, gather/scatter and finalize machinery in `ops/moe/triton/fp8.py` is already
  dtype-agnostic, so it is mostly a `wrap_torch_tensor` + scale-free `PrecisionConfig`
  + one `register_kernel` block).
- **sm_120 inherits datacenter shared-memory tiles — E28 (also implicates E27).**
  `platform.is_hopper_plus` is True for sm_120, so kernels that branch on it hand
  sm_120 tiles sized for sm_90/sm_100's ~228 KB of opt-in shared memory. sm_120 has
  only ~100 KB, the same as sm_86/sm_89. In `mha_prefill.py` this aborts the launch
  with `OutOfResources: shared memory, Required: 114688, Hardware limit: 101376` from
  **head_dim 256 up** — which is exactly the number E27 saw on Gemma-4's head_dim-512
  layers, so that failure is very likely the same bug rather than a Gemma-specific one.
  Compounding it, `PlatformInfo.max_shared_memory_per_sm` read a torch attribute that
  does not exist (`max_shared_memory_per_block`) and so reported **0 on every NVIDIA
  device**, leaving kernels with no way to ask. **Lesson: `is_hopper_plus` /
  `is_blackwell_plus` are arch-*version* predicates and say nothing about the
  shared-memory budget — size tiles off the measured budget instead.**
- **`ArchVersion` is a version number, not a capability model — E1, E3, E28, E30.**
  This is the root cause behind E28's shared-memory bug, E3's "3 datacenter
  `deep_gemm` ops win selection on sm_120", and most of what E30 found. Two
  failure shapes, both structural:
  - **Open-ended `min_arch_version`** (`(9,0)` or `(10,0)` with no max) is
    satisfied by *every* newer part. It admits sm_120 today and will admit
    sm_130 tomorrow, and it also quietly asserts that sm_100-only behaviour
    holds on **sm_103 (B300)**, which nobody has tested. Because the datacenter
    kernel sits at `SPECIALIZED`/`PERFORMANT` and the portable Triton one at
    `PORTABLE`, an over-broad `min_arch_version` is always *decisive*: it wins
    the ranking and then hard-fails.
  - **Exact-equality** (`is_blackwell` == `major == 10`) excludes sm_120 from
    things it can genuinely do. That is what kept nvfp4 unreachable (E30) even
    though sm_120 has FP4 tensor cores and the nvfp4 GEMM already passed its
    own gate — the registry ended up holding an nvfp4 *GEMM* with no nvfp4
    *quantizer*.

  E30 also found that `CapabilityRequirement.required_features` — the one
  mechanism that could express this properly — had **zero real uses**, so the
  feature vocabulary was decorative. The fix pattern, in order of preference:
  **(1)** query a real measured device property (E28's
  `shared_memory_per_block_optin`); **(2)** probe the artifact (`inspect.signature`
  on the wheel, `try/except` around the import, ask `select_kernel` who won —
  all three patterns already exist in-tree); **(3)** only if neither is possible,
  add an explicit named feature derived from a known-arch table, as E30 did with
  `compute:tcgen05`, and have kernels declare `required_features`. Never write
  `if sm_120:` — it needs redoing for sm_103, sm_121, AMD, and the next part.

  **Correction to a widespread assumption:** sm_120 *does* support thread-block
  clusters and distributed shared memory (`mapa.shared::cluster` assembles for
  `sm_120a`; the driver reports `CU_DEVICE_ATTRIBUTE_CLUSTER_LAUNCH == 1`). Do
  not take `compute:cluster` away from it. The capabilities it actually lacks
  relative to datacenter Blackwell are **tcgen05/TMEM** and the ~228 KB
  shared-memory budget.
- **vLLM flashinfer arch mis-detect — E10.** Separate from ours: vLLM's own
  flashinfer in its venv rejects sm_120 (`requires sm75+`) even with `TRITON_ATTN`.
  A vLLM-side env/wheel fix, not a UnieInfra bug. Left for later (per "don't grind").
- **C=256 saturation — E9.** Not a KV wall (KV pool 472448 tok holds ~369 seqs at
  these lengths). It's the **static CUDA-graph cap (160)**: batches >160 fall back
  to eager, and the running-batch cap queues the rest → TTFT explodes. Config-tunable
  (E13 tests it); the durable fix is making these knobs adaptive.

## Working configuration (what actually runs on sm_120 today)
Dense/GDN models **and bf16 MoE** (E28), `attention_backend=triton`,
`enforce_eager=False` (CUDA graph), `disable_custom_all_reduce=True`, single GPU.
MoE additionally wants `disable_kvstore=True` (E17) and, on a 96 GB card holding
66 GB of weights, **concurrency ≤ ~32 until the GDN mamba-pool over-admission in
E28 is fixed**. See `docs/guides/build-and-run.md` for the full reproducible steps
and the env shims.

**On the vLLM base (`--quantization unieinfra`, E34/E38):** bf16, fp8 (online,
from a bf16 checkpoint) and NVFP4 (ModelOpt checkpoint) all run. NVFP4 on sm_120
needs two shims that stock vLLM does not apply for itself —
`--linear-backend cutlass` and `--attention-backend TRITON_ATTN` — without which
even stock `--quantization modelopt_fp4` fails to start, because both default
paths land on FlashInfer's JIT and it rejects `major == 12`.

**Weight precision on the dense path:** bf16, `--quantization fp8` (E23) and
**nvfp4 from a ModelOpt checkpoint** (E30) all run. nvfp4 is the fastest measured
(C=128 4341 tok/s) and needs no extra flags — point `tokenspeed serve` at an
NVFP4 checkpoint such as `nvidia/Qwen3-8B-NVFP4` and the quant config is detected
from `hf_quant_config.json`. There is no *online* nvfp4 quantization path, and no
accuracy evaluation has been run at fp4. See `docs/support-matrix.md` for the
measured table.
