摘要

在 4 張 AMD MI350P（gfx950、PCIe、TP4）上跑 DeepSeek-V4.1-Flash 的 AgentX 工作負載，UnieInfra 以各自最佳設定對比 vLLM 最佳設定：c4 與 c16 達 1.29–1.30 倍、c1 達 1.62 倍、c128 達 5.65 倍 RPM；c32 與 c64 為 1.09–1.12 倍，仍未到 1.3 倍目標。

條件：AgentX 壓力模式（移除 think time）、每格 600 s、T=1.0 取樣、雙方 GPU memory utilization 0.9（UnieInfra c128 為 0.86）、vLLM 取 recipe cap（CONC/4）與 2×CONC 兩者較佳者；c4–c64 為兩次平均，全部 0 錯誤。最終設定為 coupled DSpark drafting + block verification + prefill 兩 micro-batch 通訊重疊（TOKENSPEED_PREFILL_TBO=1），全部 lossless，不使用量化通訊。

三個主要結論：

  • 容量決定高並行度：UnieInfra 每 token 的 KV 約 940 B，vLLM 約 2090 B；c128 時 vLLM 放不下工作集，prefix cache 大量被逐出。

  • c4–c64 由 decode 與 prefill 每步效率決定：GPU-only profile 顯示 all-reduce 佔 kernel 時間 37%（PCIe 頻寬受限），MoE 佔 25%；把 prefill all-reduce 藏到計算後面是 c16 跨過 1.3 倍的關鍵。

  • 方法論比優化更常出錯：greedy vs sampling、官方 vs 壓力、單次 600 s 格 ±10–15% 雜訊、profiler 放大 Python 成本 35–40 倍、測試意外載入不同 MoE kernel，這些都曾讓結論翻盤，第 3 節逐一記錄。

Kernel 層優化

Kernel 工作把 130K context decode 從明顯落後 vLLM 拉到持平：64 人 130K 共享前綴 decode 從 30.0 ms/token 降到 21.6 ms/token（vLLM 同 bench 21.6）。主線是「MI350P 不是 MI355X」：128 CU / 4 XCD，而很多 gfx950 kernel 寫死 256 CU / 8 XCD。

  • ROCm decode query 只補到 16 heads（e8189f55，原本照 FlashMLA 補到 64）：64 人 24.3 → 22.8 ms/token。

  • DSpark 草稿注意力改走 sparse kernel（d164aa89）：0.77 → 約 0.1 ms/call，每步省 2.3 ms。

Dense GEMM

移植 vLLM/aiter 的 block32 MXFP8 GEMM（tiled + packed、fused split-K）並針對 128 CU 重調（83d49991）：M=96 時每次快 2–3×（wo_b 29.0 → 10.5 µs），每步省約 2.8 ms；約 5% 輸出與精確 BF16 路徑差 1 ULP。

MoE：gluon（內建）vs aiter

MoE 在 decode 是權重頻寬受限：192 rows 時 384 個 expert 幾乎全部被啟用，每步要讀約 75 GB/GPU 的 MXFP4 權重，實測約 3.2 TB/s。vLLM 的 AMD recipe 用 aiter 的 FlyDSL a8w4。我們把 aiter backend 正式接進來（MOE_BACKEND=aiter），並修掉它載入權重時的 12–14 GB 記憶體碎片（預配 padded buffer、每 32 個 expert 原地 shuffle，a5ae4510）。兩次交錯重複量測後與 gluon 打平（c16 70.05 vs 70.5、c32 112.0 vs 108.5、c64 137.6 vs 139.3 RPM），為 128 CU 重調 aiter 參數也只有 t16 快 7%，所以不採用。

通訊

純 PCIe 的 TP4 讓 all-reduce 成為最大單項成本：AgentX c32 的 GPU-only trace 中佔 kernel 時間 37%，其中 prefill 大小的全縮佔總時間 21%、decode 大小佔 13%。

Iris all-reduce

  • prefill 大小改走 Iris（db3956be）：168 MB 時 RCCL 6.19 ms、Iris two-shot 5.51 ms，約 55 GB/s（PCIe 上限）；104K prompt prefill 4.15 → 3.67 s。

  • 小訊息的 program 上限（0f528991）：decode 大小（1–4 MB）時 84 個 programs 比需要的慢 2–2.7×；2 MB 以下改 32 programs，16 人 11.85 → 10.6 ms/token。

  • decode 的 all-reduce 是延遲受限：每步約 90–109 次、每次 110–130 µs。INT8 壓縮、one-shot 改 two-shot、與 mHC post 融合三種方向都量過，結果中性。

INT8 / FP8 two-shot（有損，預設關閉）

fce19969 / 4f519968 重寫 8-bit Iris pull two-shot：全 grid quantize kernel、每 128 一個 FP32 scale、16-byte peer load。168 MB 5.12 → 2.81 ms（1.82×），相對誤差 9.3e-3，GSM8K 93.0%。壓力模式 c32 +12%、c128 +28%。因為是有損通訊、vLLM 沒有使用，公平比較一律關閉（TOKENSPEED_IRIS_Q8_ALLREDUCE=0）。

通訊與計算重疊：先失敗、再成功

  • row-chunked FFN 重疊（#32、#49）：RCCL 或 Iris-32 放 side stream，單一長 prompt 的 prefill 反而慢 5–15%。

  • decode 兩 micro-batch（評估）：MoE 拆半變 1.65×、GEMM 1.6×，即使 all-reduce 全藏每步仍慢 7 ms；實測重疊的總時間反而比序列長。不做。

  • prefill 兩 micro-batch（TBO，6361be94）：只對 ≥4096 rows 的 pure EXTEND。把一個 chunk 在請求邊界或 128 對齊處切成 A、B，B 視為同一請求的下一個 chunk。每層 compute stream 依序跑 attn(A)、attn(B)、MoE(A)、MoE(B)，同時 side stream 對另一半做 all-reduce；每半有自己的 Iris producer lane（32 programs），mHC post 拆成獨立 kernel。

TBO 成功的關鍵是 stream priority：ROCm 把同 priority 的 stream 輪流分到 4 個 HW queue，side stream 跟 compute stream 落在同一個 queue 就會完全序列化。第一版 trace 重疊 0 ms，改成 priority=-1 後，2574 ms 的 all-reduce 有 2236 ms 被藏住。先前 #32/#49 的失敗很可能是同一個原因。

深入：prefill 兩 micro-batch 通訊重疊（TBO）

一句話：把一個 prefill chunk 切成 A、B 兩半，讓一半在做 all-reduce 的時候另一半在計算，把 PCIe 通訊時間藏起來。

為什麼需要

TP4 下每一層要做兩次 all-reduce：一次在 attention 輸出投影之後、一次在 MoE 之後，把 4 張 GPU 各自算的部分和加起來。prefill 一次處理 8192 個 token，每次 all-reduce 要搬約 8192 × 5120 × 2 bytes ≈ 84 MB。這台機器的 GPU 之間只有 PCIe（約 55 GB/s），所以一次要 1.7 ms 左右，而且這段時間 GPU 的計算單元幾乎沒事做。AgentX c32 的 profile 裡，這類 prefill 大小的 all-reduce 佔了總時間的 21%。

怎麼切

  • 只對大的 prefill 生效：純 prefill 的 step、至少 4096 個 token（TOKENSPEED_PREFILL_TBO_MIN_ROWS）。小的 prefill 切半後 GEMM 太小，得不償失。decode 路徑完全不動。

  • 切點：優先切在兩個請求之間（靠近中間）。如果整個 chunk 只有一個請求，就切在該請求內一個 128 對齊的位置。

  • 因果關係怎麼保持：被切開的請求，B 那半就當成「同一個請求的下一個 chunk」。同一層裡 A 先跑 attention，把自己的 KV（sliding window、壓縮後的全域 KV、壓縮器尾端）寫進 cache；B 的 attention 再從 cache 讀到 A 的內容。這跟一般的 chunked prefill 是同一個機制，只是發生在同一層內。

  • metadata：attention backend 的 plan_prefill_micro_batches() 一次準備好 A、B、整體三份 forward metadata，執行時用 use_forward_state() 切換。

  • 只重疊前段層：DSv4.1 的 prefill 後段層只算每個請求的尾端 token（narrowing），資料量小、不值得切，維持原樣。

通訊端的設計

  • 每半一個 Iris producer lane：A、B 各有自己的通訊緩衝區，可以同時在途（多佔約 320 MB，只在開啟時配置）。

  • 32 個 programs：Iris 的 all-reduce 是靠 GPU 上的 workgroup 在輪詢（spin），會佔走計算單元。用 84 個時只能藏住 17% 的通訊，降到 32 個能藏住 62–64%。

  • mHC post 拆開：原本 all-reduce 與 mHC post 是融合的一個 kernel，但 program 數少時融合版太慢，改成 plain all-reduce + 獨立的 mHC post kernel。

關鍵：stream priority

第一版做完後 trace 顯示重疊時間是 0 ms，prefill 也沒變快。原因是 ROCm 會把同一個 priority 的 stream 輪流放進 4 個硬體佇列（HW queue），當通訊 stream 跟計算 stream 剛好分到同一個佇列，硬體就會一個一個依序執行，程式上看起來是兩個 stream，實際上完全序列化。把通訊 stream 建成 priority=-1（較高）後，它一定落在另一個佇列，trace 中 2574 ms 的 all-reduce 有 2236 ms 被藏住，104K prompt 的 prefill 從 5.1 s 降到 3.9 s。先前兩次重疊嘗試（#32、#49）也用預設 priority，很可能就是同一個原因失敗。

代價與限制

  • 數值：通訊完全 lossless；attention 切成兩段、GEMM 的 batch 形狀改變，數值差異與一般 chunked prefill 相同。

  • 只支援 TP（attention 與 MoE 用同一個 TP group），不支援 EP / DP。

  • 只在 eager prefill 生效（chunk 大於 prefill graph 上限時）。

排程與 KV cache

c128 的 5.6 個倍數幾乎全部來自 KV 容量：同樣 0.9 的記憶體預算，UnieInfra 存 3300–4400 萬 tokens，vLLM 存 1460–1855 萬。

KV 佈局：每 token 約 940 B vs 2090 B

DSv4.1 的注意力本身是壓縮的，UnieInfra 的 LCM cache arena 照結構分組配置（server log 的 Cache profile 行：global_r1 140、global_r2 45、compressor_tail_r2 8、swa 2）：

  • 全域層：存壓縮後的 KV，每幾個 token 一筆，長 context 的邊際成本很低。

  • sliding-window 層：每請求只留最近一段視窗，不隨 context 增長。

  • 壓縮器尾端：只存未湊滿一個壓縮單位的尾巴；每頁 2 列 → 32 列（0f528991）讓 13 萬 context 的 block table 從 69K 欄縮到 4.3K 欄。

  • 一起配置：各組以最小公倍數頁一起分配、比對前綴、釋放。

排程

  • decode 饥餓（#38、cfaac28b）：非 mixed 模式下一個 round 有 prefill 就不 decode，c128 queue 永遠不空，結果 0 完成。TOKENSPEED_DECODE_EVERY_PREFILL_ROUNDS=1 讓它變成 21.4 RPM。

  • cache-aware admission（e2317c72）：依裝置上已快取的前綴長度排序申請、最多超車 64 次；c128 命中 0% → 65%。

  • GIL 競爭（fcbe6e2d）：ExecutionPlan.forward 在 GIL 下複製 MB 級 block table、reserve() 每次 O(table)；修掉後每步 idle 5.3 → 4.2 ms。

  • prefill chunk：16K → 4K 在開 INT8 時 c4 ITL p99 66 → 25 ms；最終設定用 8K，8K、4K、8K+graph 8192 在 c32 上於雜訊內（108.0 / 112.9 / 107.2–112.3）。

  • mixed batch（decode 搭乘 prefill round）：小並行度有利、c64 不利，最終關閉。

投機解碼

在 T=1.0 取樣下，每步接受的 token 數從 2.8（獨立取樣）提升到 3.1–3.2（coupled drafting），再提升到 3.3–3.9（block verification）；兩者都是 lossless，輸出分布等於目標模型。

Coupled DSpark drafting（5e0db812）

草稿的每一步用與驗證器同一組 Philox Gumbel 噪聲取樣：草稿第 s 步對應驗證第 s 列，offset = start_pos+2+s。驗證器仍是「目標取樣後精確比對」，所以輸出就是目標的樣本；當草稿與目標分布接近時，共用噪聲讓兩邊抽到同一個 token 的機率接近 1−TV。同一 build、同一 chunk 大小下，相對獨立取樣：c4 +2.4%、c16 +11.6%、c32 +10.6%、c64 +2.9%。草稿溫度倍率 0.7 / 1.0 / 1.4 測過，1.0 最好。

Block verification（Sun et al. 2024）

整個草稿塊聯合接受，而不是逐 token 判斷：

p_i = \min\!\left(1,\; p_{i-1}\,\frac{P(x_i)}{Q(x_i)}\right),\qquad h_i = \frac{R_i}{R_i + 1 - p_i},\qquad R_i = \sum_x \max\big(p_i P(x\mid x_{\le i}) - Q(x\mid x_{\le i}),\,0\big)

最後一個位置 h = p；接受滿足 u_i ≤ h_i 的最長前綴，下一個 token 從 max(p·P − Q, 0)（整塊接受時從 P）取樣。實作需要完整詞表的草稿 logits：草稿每步的 local logits 存進 [slots, 5, local_vocab] pool，驗證時重建 base + Markov bias 並跨 TP all-gather。

深入：block verification

一句話：草稿提出的一整串 token，不再一個一個獨立判斷「要不要收」，而是整串一起看；後面 token 的「好」可以補貼前面 token 的「不夠好」，所以每步平均能接受更多 token，而輸出的機率分布完全不變。

背景：投機解碼靠「每步收幾個 token」賺錢

DSpark 的小草稿模型每步先猜 5 個 token，大模型用一次 forward 同時算 6 列（原本一列 + 每個猜測一列）的機率，再決定收下前幾個。大模型一次 forward 的成本幾乎固定，所以「每步收下的 token 數」直接決定 decode 速度。AgentX 的請求帶 temperature 1.0，必須用取樣來驗證，不能只比對「最可能的 token」。

逐 token 驗證 vs 整塊驗證

  • 逐 token（標準做法）：第 i 個草稿 token 以 min(1, P/Q) 的機率收下；一旦某個被拒絕就停，後面的全部丟掉。每個 token 只看自己。

  • 整塊（Sun et al. 2024）：從第一個開始累積一個「信用」 p。P/Q > 1 的 token（大模型比小模型更想選它）會把信用往上拉，後面的 token 可以用到。最後接受「滿足 u ≤ h 的最長前綴」，而不是在第一個失敗就停。

完整公式見上方的 p、h、R 定義。直覺上：R 是「如果在這裡停下，還有多少機率量可以拿來重新抽樣」，h 用它把「在這裡停」與「繼續」的機率分配好，讓最後產生的 token 序列機率剛好等於大模型自己取樣的機率（lossless）。停下時的下一個 token 從殘差 max(p·P − Q, 0) 抽，整塊都收下時則直接從 P 抽。

實作：難在需要完整詞表的 Q

逐 token 驗證只需要草稿 token 本身的 Q，整塊驗證的 R 要對整個詞表加總，所以要草稿模型在 129K 個詞上的完整機率。但 TP4 下每張 GPU 只算 1/4 詞表：

跟 coupled drafting 的關係

兩者同時開啟：草稿端用 coupled Gumbel 噪聲取樣（讓草稿更常猜中目標會抽的 token），驗證端在 ≤128 個請求時用 block verification、否則用原本的「目標取樣後精確比對」。兩條路徑輸出都正確，只是每步接受數與成本不同，所以可以一步一步自動切換。

效果

GSM8K（T=1.0）每步接受 2.1–3.7 → 3.3–3.9 個 token，準確率 96.2% → 95.8%（雜訊內）。AgentX 壓力模式（只差這個旗標）：c1 +19%、c32 +8%、c16 +5%、c4 +3%、c64 +2%；c1 的每 token 生成時間（ITL p90）從 9.4 降到 6.1 ms，比 vLLM 的 7.5 ms 還快。

穩定性與正確性

KV 依記憶體預算長滿時，約 5% 的啟動會在長 prefill 中以 HSA_STATUS_ERROR_OUT_OF_RESOURCES 崩潰；留約 6 GB/GPU 餘裕（gmu 0.86）後穩定。

HSA OUT_OF_RESOURCES

  • 共同點：8 個崩潰的 abort 訊息都是 Available Free mem : 0 MB，都在 4K–16K new token 加數十萬到數百萬 cached token 的 chunked prefill 中；7/8 在 abort 前 ≤2 秒四個 rank 都出現 HIPCachingAllocator ... OOM (free: 0)。

  • 機制：AQL queue 的動態 scratch handler 配置失敗時回報這個錯誤。KV 預算 = profile 後可用記憶體 − 0.1×144 GB，這 14.4 GB 在 ready 前已被 graph、retraction pool（4 GB）、non-torch（約 8.8 GB）吃掉大半。

  • 副因：啟動腳本的 -e HSA_NO_SCRATCH_RECLAIM 沒帶值，docker 把 image 內建的 =1 刪掉，ROCr 因此會回收 scratch 後重配。修正後仍在 gmu 0.9、40.3M tokens 下崩潰，所以主因是記憶體用滿。

aiter MoE 的記憶體碎片

舊的 preprocessor 整層 pad 再 shuffle，產生 1.26 GB / 1.26 GB / 0.63 GB×2 的暫存；釋放的大 block 被之後的小常駐 tensor 切走釘住，empty_cache 收不回，40 層後約 17.4 GB（單 GPU repro）。第一版修正用 max_split_size_mb:32 反而在真實 4-rank server 載入時 OOM；最後改成預配 padded buffer、每 32 個 expert 原地 shuffle、不在每層 empty_cache（a5ae4510），c128 連續啟動 3 次 4/4 rank 無 OOM，KV 36.9–37.6 GB（gluon 36.5）。

正確性驗證

  • needle-in-haystack 6/6：每個 kernel commit 與 TBO 都有跑。

  • GSM8K：T=0 的 CI 設定在 kernel 系列為 92.3–93.6%（門檻 90%）；T=1.0 設定用來驗 block verification（95.8 vs 96.2%）與 TBO（90.7 vs 91.2%）。

  • prefix cache：三個 105K 文件的冷 / 續輪 / 重複請求檢查，續輪 TTFT 3.5 → 0.08 s、答案正確，重複請求輸出與冷請求相同。

剩餘瓶頸與下一步

c32–c64 要從 1.1× 到 1.3×，還需要每步再快約 15–20%；GPU 有 89% 時間在算，所以剩下的空間大多在 kernel 本身，尤其是 all-reduce 與 MoE。

依把握程度排序的下一步：

  1. 把 prefill 重疊併入 PR：已用 4 次開 / 4 次關的 AgentX A/B 驗證，c16 +26.6%、c32 +10.7%，needle 與 GSM8K 未退化。

  2. decode all-reduce（約 13% 牆鐘時間）：壓縮、幾何、融合、重疊都試過；剩下的是更低延遲的同步設計（例如 vLLM nvidia/specialized_decode 的 Lamport 式 all-reduce，把 mHC post / RMSNorm / MXFP8 量化一併融合），預估每步 3–5 ms。

  3. MoE 頻寬效率：目前約 3.2 TB/s，若達 85–90% 的 HBM 上限可省 2–3 ms/步；aiter 已證實不更快，要從 gluon kernel 本身下手。

  4. 每步主機準備：真實閒置約 6–11%，最大一段是清 cache 頁後的 HtoD（每步約 2.8 ms、約半數步驟）。

  5. 需使用者決定：INT8 prefill all-reduce（有損，先前 c32 +12%、c128 +28%）。
